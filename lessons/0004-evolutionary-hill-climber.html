Part 4 • Evolutionary Algorithm

The Evolutionary Loop & Hill Climber Strategy

Implement an asynchronous (1+1) Evolutionary Strategy in Kotlin, coordinate lock-free state across background worker threads, and understand genetic convergence dynamics.

1 The (1+1) Hill Climber Strategy

In classic genetic algorithms for symbolic optimization, you typically maintain a population of hundreds of candidates and apply sexual crossover (slicing two genomes in half and splicing them together).

However, for image approximation with hundreds of semi-transparent vector strokes, crossover is disastrous: stroke #42 from Parent A was tuned to blend specifically over strokes #1–41 of Parent A. Splicing it into Parent B produces visual disharmony and sharp fitness regressions.

Instead, the gold standard in evolutionary art is the (1+1) Evolutionary Strategy (also known as a stochastic hill climber with mutation):

1
Champion
Maintain current best painting candidate.
⬇
2
Stochastic Mutation
Clone champion and mutate a single gene or stroke order.
⬇
3
Offscreen Evaluation
Compute L1 pixel difference against target image.
⬇
4
Selection Decision
If mutant error ≤ champion error, mutant becomes new champion! Else discard.

2 Multi-Threaded Architecture

In a graphical desktop app, the AWT Event Dispatch Thread (EDT) is responsible for handling OS window events, keyboard shortcuts, and rendering frames at 60 FPS.

⚠️ Never Run Evolution on the UI Thread!
If you run the evolutionary loop on the main UI thread, your desktop window will immediately freeze and stop responding to mouse or keyboard events.

We spawn an independent, high-priority background worker thread:

Worker Thread Spawning 
thread(name = "genetic-worker", isDaemon = true) {
    while (running.get()) {
        if (paused.get()) {
            Thread.sleep(20)
            continue
        }
        step()
    }
}

3 Lock-Free State Synchronization

Because the worker thread generates thousands of mutations per second while the UI thread reads the current best painting at 60 FPS, we must prevent race conditions without using heavy, blocking locks.

Kotlin and the JVM provide lock-free java.util.concurrent.atomic primitives:

  • AtomicBoolean: Used for running and paused control flags.
  • AtomicLong: Used for generations, acceptedMutations, and currentEvalsPerSec.
  • AtomicReference<Painting>: Holds the pointer to the latest accepted champion painting. The UI thread reads this pointer with zero synchronization locks:
Lock-Free Atomic Reference 
private val bestPaintingRef = AtomicReference()

fun getBestPainting(): Painting = bestPaintingRef.get()

private fun updateBestPainting(newChampion: Painting) {
    bestPaintingRef.set(newChampion)
}

4 The GeneticPainter Engine

Examine GeneticPainter.kt in your project:

src/main/kotlin/GeneticPainter.kt 
class GeneticPainter(
    val target: TargetImage,
    initialStrokeCount: Int = 120,
) {
    private val evaluator = Evaluator(target.width, target.height, target.pixelBytes)
    private val bestPaintingRef = AtomicReference()

    fun step() {
        val champion = bestPaintingRef.get()

        // 1. Mutate
        val mutant = champion.mutate(target.width.toFloat(), target.height.toFloat())

        // 2. Evaluate fitness
        val mutantError = evaluator.evaluate(mutant)

        // 3. Selection
        if (mutantError <= champion.error) {
            val acceptedPainting = mutant.copy(error = mutantError)
            bestPaintingRef.set(acceptedPainting)
            acceptedMutations.incrementAndGet()
        }

        generations.incrementAndGet()
    }
}

6 Understanding Convergence Phases

When you run the algorithm, you will observe distinct stages of convergence:

🚀 Phase 1: Macro Approximation (0–5k gens)

Acceptance rate is high (~15–30%). Large strokes cover the canvas, establishing the dominant color palette and rough silhouettes.

🔬 Phase 2: Micro Refinement (5k–100k+ gens)

Acceptance rate drops to ~1–3%. Mutations fine-tune individual edge curves, subtle shading gradients, and highlight accents.

7 Knowledge Check

Check your storage strength on concurrency and evolutionary strategy design.

Why is crossover omitted in favor of a (1+1) mutation strategy for vector art?
Kotlin collections lack crossover support.
Crossover doubles fitness evaluation time.
Splicing strokes destroys visual layering.
Atomic references cannot synchronize populations.
